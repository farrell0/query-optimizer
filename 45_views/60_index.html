Preparing
In our data: A table t1 with 500,000 rows split into two very different populations under one customer_id column — 500 "typical" customers with ~100 rows each (50,000 rows total), and 3 "mega" customers with 150,000 rows each (450,000 rows total, ~90% of the table). Indexed on customer_id.
The query: a single prepared statement, held open on one persistent connection the way a pooled application would — PREPARE find_by_customer(int) AS SELECT id, customer_id, payload FROM t1 WHERE customer_id = $1; — then repeatedly EXECUTE find_by_customer(<id>). Click Typical a few times, then click Mega: Postgres's planner will have already settled on one reusable plan shaped by the typical calls, and the mega customer's query pays for it.

Query plan management

Automatic detection of the regression shown on the Query tab.

Query Plan Management (QPM) tracks every distinct plan the demo query has produced (yb_pg_stat_plans) and flags when the plan currently in use doesn't match the best one on record (yb_pg_stat_plans_insights, Needs review below). Run some queries on the Query tab first, then come back here.
